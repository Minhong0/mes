## 2026-10-17 POP

| 항목 | 결정 | 이유 | 검토한 대안 |
| --- | --- | --- | --- |
| POP 로그인 | 사번만 입력 (비밀번호 없음), 요청마다 workerId 전송 | 현장 단말은 여러 작업자가 돌려 쓰고 사원증 바코드로 찍는 경우가 많음. 인증은 이후 단계에서 추가 | 세션·JWT 로그인 |
| 실적 중복 방지 | POP가 요청마다 GUID(request_id)를 붙이고 서버가 필터 UNIQUE 인덱스로 한 번만 저장 | 응답을 못 받은 POP가 다시 보내도 실적이 두 번 생기지 않음 (설비 message_id와 같은 방식) | 수량 비교로 중복 추정 |
| 실적 수정 | 수정 없이 취소 표시 후 재등록 | 누가 언제 바꿨는지 남음 (감사 추적) | UPDATE |
| 화면 로직 테스트 | ViewModel이 IMesApi, IDialogService에만 의존 | 서버·창 없이 xUnit으로 재전송·입력 잠금 규칙을 시험 | UI 자동화 테스트만 |

## 2026-10-18 POP B (품질, 정지 사유, 단말 보관)

| 항목 | 결정 | 이유 | 검토한 대안 |
| --- | --- | --- | --- |
| OEE 품질의 불량 | 생산 수량은 설비 카운트, 불량은 그날 POP 실적의 합(취소 제외). 양품 = 생산 − 불량 | 설비는 몇 개를 깎았는지 정확히 알지만 불량은 사람이 봐야 앎. 각자 잘 아는 숫자를 씀 | 생산 수량도 POP 실적으로 (입력 누락에 약함) |
| 불량 > 생산 | 경고를 남기고 생산 수량까지만 반영 | `prod_qty = good_qty + defect_qty` 제약을 지키고, 카운트 누락이나 오입력을 로그로 찾게 함 | 생산 수량을 불량에 맞춰 올림 (성능 지표가 부풀려짐) |
| 다시 집계할 때 | 실적 등록·취소 커밋 후 이벤트로 날짜를 모아 두고, 1분 스케줄러가 집계 | 요청 처리를 늦추지 않고, 같은 날 실적 여러 건을 한 번에 집계. 집계가 실패하면 날짜를 되돌려 다음에 다시 함 | 요청 안에서 바로 집계 (POP 응답이 느려지고, 집계 실패가 실적 저장까지 되돌림) |
| 정지 사유 | 설비가 남긴 정지(downtime 행)의 사유를 작업자가 확정. 원래 행을 고치고 확정자·시각(reason_at)을 남김 | 설비는 멈춘 것만 알고 이유는 현장이 앎. 같은 행이라 파레토·모니터링 쿼리를 바꿀 필요가 없음 | 사유를 별도 테이블에 쌓기 (조회가 복잡해짐), 설비 사유를 그대로 둠 |
| 사유 확정 API | PUT (같은 내용으로 다시 보내도 결과가 같음) | 응답이 없으면 그냥 다시 누르면 됨. 실적처럼 요청 ID가 필요 없음 | POST + 요청 ID |
| 보내지 못한 실적 | 보내기 **전에** 단말 파일(작업자별 JSON)에 적고, 저장·거절이 확실해지면 지움. 다음 로그인 때 자동으로 다시 보냄 | 응답 대기 중 POP가 꺼져도 요청 ID가 남아 중복 없이 다시 보낼 수 있음 (시뮬레이터 outbox와 같은 생각) | 실패했을 때만 저장 (보내는 중에 꺼지면 사라짐), 여러 건을 쌓는 오프라인 큐 (서버 확인 없이 계속 입력하게 되어 계획 수량·상태 검사를 못 함) |
